# TIDE Framework 🛰️

### Technician & Infrastructure Detection Environment

> A practical framework for real-time monitoring, incident detection, and evidence preservation across authorized technician, administrator, and manager workspaces.

TIDE provides a lightweight approach to monitoring **company-owned or explicitly authorized workstations and servers**.

The objective is simple:

**Observe → Detect → Investigate → Respond → Preserve**

TIDE can complement frameworks such as **SCOPE** by moving from compliance assessment into **continuous operational visibility**.

# T — Traffic

Monitor network activity generated by local processes.

## Install NetHogs

```bash
sudo apt update
sudo apt install nethogs
```

Run:

```bash
sudo nethogs
```

NetHogs provides a process-oriented view of network bandwidth usage.

Useful questions:

* Which process is consuming bandwidth?
* Is an unexpected process communicating externally?
* Did network activity suddenly increase?
* Is an unauthorized application communicating with the Internet?

---

# I — Inspect

Monitor processes and system activity.

## Install Sysdig

```bash
sudo apt install sysdig
```

Basic process/user-oriented inspection:

```bash
sudo sysdig -c spy_users
```

Sysdig can provide deeper visibility into:

* Processes
* System calls
* Users
* Files
* Network activity
* Process execution

For incident investigation, this can help establish **what actually happened on the endpoint**, rather than relying exclusively on application logs.

---

# D — Detect

Monitor filesystem activity in real time.

## Install inotify-tools

```bash
sudo apt install inotify-tools
```

Monitor a specific workspace:

```bash
inotifywait -m -r ~/workspace \
  -e create,modify,delete,move
```

Example output:

```text
workspace/file.txt MODIFY
workspace/new_script.sh CREATE
workspace/config.yml MODIFY
workspace/old.log DELETE
```

### Why monitor a specific workspace?

Avoid blindly monitoring the entire filesystem:

```bash
inotifywait -m -r /
```

Monitoring `/` can generate enormous amounts of telemetry and create unnecessary system load.

Instead, define monitored locations explicitly:

```text
/home/technician/workspace
/opt/company/application
/etc/company
/var/log/company
```

# E — Evidence

Detection is only useful if the event can later be investigated.

TIDE should preserve:

```text
Timestamp
    ↓
Hostname
    ↓
User
    ↓
Process
    ↓
Action
    ↓
Resource
    ↓
Network destination
    ↓
Result
```

Example event:

```json
{
  "timestamp": "2026-09-01T18:30:42Z",
  "hostname": "tech-workstation-01",
  "user": "technician",
  "event": "file_modified",
  "path": "/home/technician/workspace/config.yml",
  "process": "vim",
  "severity": "low"
}
```

The goal is to turn raw endpoint activity into **investigable events**.

# 🧠 TIDE Principles

### 1. Observe Before Assuming

Raw telemetry should be collected before drawing conclusions.

### 2. Detect Before Responding

An unusual event is not automatically malicious.

### 3. Preserve Before Cleaning

When an incident is suspected, preserve relevant evidence before modifying the environment whenever practical.

### 4. Minimize Telemetry

Collect what is necessary for the security objective.

### 5. Authorized Endpoints Only

TIDE is intended for:

* Company-owned devices
* Managed infrastructure
* Explicitly authorized environments

Employees and contractors should receive appropriate notice and monitoring should comply with applicable law, contracts, and company policy.

### 6. Logs Are Evidence

Logs should be:

* Timestamped
* Integrity-protected
* Access-controlled
* Retained according to policy
* Exportable for investigation
